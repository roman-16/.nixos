# Changelog

Write the line a stranger reads to decide whether and how to upgrade. A changelog is a curated list of notable changes for humans, not a rendering of the git history: a commit documents a step in the source's evolution, an entry documents the difference that a user of the project can feel, often across several commits. If an entry could have been generated from `git log`, it is the wrong entry.

That decision turns on one thing: what moved on the surface the reader touches - the commands they type, the calls they make, the settings they set, the screens they see. Work that leaves that surface untouched, however large, is invisible to them and belongs nowhere in this file.

## Scope

- Writes exactly one file: the project's `CHANGELOG.md`.
- Reads git (`git diff`, `git log`, `git tag`, `git remote get-url`) and never mutates it. No committing, no tagging, no pushing - committing is the `commit` skill's job, under its own approval.
- Never bumps versions in `package.json`, `pyproject.toml`, `flake.nix`, or anywhere else.
- Never rewrites released sections, and never reformats the file as a side effect of adding to it.
- Regenerating a whole changelog from history is a different job. It needs the user's explicit go-ahead and the same curation as a single entry.

## Pick the mode

| Situation | Mode |
| --- | --- |
| A change to record | [Add an entry](#add-an-entry) |
| Shipping a version now | [Cut a release](#cut-a-release) |
| Recording the work and shipping it in one go | [Add an entry](#add-an-entry), then [Cut a release](#cut-a-release) |
| Project has no `CHANGELOG.md` | [Create the file](#create-the-file), then add the entry |

## Add an entry

### 1. Find the file, and check who owns it

Take the `CHANGELOG.md` nearest the changed files, walking up to the repository root. In a monorepo, that is the changed package's own changelog; when several are plausible, ask which one.

Stop and tell the user instead of editing when the file is machine-owned: a `.changeset/` directory, `release-please-config.json`, `cliff.toml`, `towncrier` news fragments, a `## [Unreleased]` section stamped "generated by", or a release CI job that rewrites it. There the entry belongs in that tool's input, and a hand edit gets clobbered on the next release.

A job that only *reads* the file is the opposite case, not the same one. Where CI takes a release's version or its notes from `CHANGELOG.md`, the file is the source of truth and this entry matters more than usual, not less: it is what the release will say. Write it, and note that [cutting a release](#cut-a-release) in such a project is what ships the software.

### 2. Read the whole file and copy its conventions

Read it end to end before touching it. The file, not the specification, decides every question it already answers: bullet marker (`-` or `*`), whether entries end with a period, whether they carry issue or PR links, sentence voice, heading style, blank-line pattern, whether the bottom link-reference block exists, and even non-standard category names.

A new entry must be indistinguishable from the entries already there. Where the file is silent, follow [the format rules](#format-rules). Where the file contradicts them, follow the file and mention the deviation once - consistency within one changelog matters more than conformance, and silently mixing two conventions is worse than either.

### 3. Establish what changed

Arguments passed to the skill are the change; use them as the subject, still filtered, categorized and worded by the rules below. Otherwise derive it, in this order: the staged diff, the unstaged diff, then the commits since the last released section. Prefer what you already know from the session over re-reading diffs.

### 4. Name the surface

`read` the sibling `../_shared/surface.md` and establish, once, which surface this project has and what it consists of.

A project with two audiences has two surfaces - a CLI that is also a library owes entries on both - and every entry names an element of one of them.

### 5. Keep only what moves the surface

One test per candidate change: **name the surface element it moves.** A command, subcommand, flag, argument, output line or exit code; an exported signature or its semantics; an endpoint, its request or its response; a config key, env var, default, file or wire format; a screen, control, message or error text. If you cannot name one, there is no entry - not a shorter entry, none.

| Candidate | Verdict |
| --- | --- |
| A new `--dry-run` flag | Entry, it names a flag |
| `sync` renamed to `push` | Entry, and breaking: name the new spelling and what the reader must update |
| Same command, different output shape | Entry, output is surface |
| A command the reader runs is perceptibly faster | Entry, naming the command and the difference |
| The test suite is twice as fast | No entry, nobody outside the repository runs it |
| A module split with identical behavior | No entry |
| A dependency bump nobody has to act on | No entry. Only when it raises a minimum runtime version, changes a requirement, or fixes a vulnerability the reader is exposed to |
| A build or CI pipeline change | No entry, unless the project ships that pipeline |
| Formatting, comments, coverage, internal docs | No entry |

Nothing at all is a normal outcome. When the work moves no surface element, say so and write no entry; never reach for the nearest internal change to fill a section.

No entry either for a bug introduced and fixed inside the same unreleased cycle. It never reached anyone, so there is nothing to tell them; do not file a `Fixed` against an `Added` that is still sitting in `[Unreleased]`.

Be consistent about this. A changelog that covers only some of the surface changes is more dangerous than none, because readers treat it as the single source of truth.

### 6. Categorize

Six categories, always in this order. It is the specification's order, not alphabetical, and it stays that way.

| Category | Owns |
| --- | --- |
| `Added` | Something exists that did not exist before. |
| `Changed` | Something that existed behaves differently. |
| `Deprecated` | Still works, still there, but on the way out. |
| `Removed` | Gone. |
| `Fixed` | Behaved wrongly in a released version, now behaves as intended. |
| `Security` | A vulnerability, and what it exposed. |

Never invent a category. There is deliberately no `Breaking` section: breaking changes live under `Changed` or `Removed` and are made unmissable in the entry itself. If you write nothing else well, write the deprecations, removals, and breaking changes - they are what an upgrade hinges on.

A `Deprecated` entry names its replacement. A `Removed` or breaking entry names the migration.

One change per bullet. A single piece of work may owe entries in several categories; split it.

### 7. Word it

- One line per entry, stating the effect, not the mechanism.
- Open on the surface element you named, never on the file, function, class or module behind it. No "refactored X into Y", no commit hashes.
- `Added` reads as the thing gained. `Changed`, `Deprecated`, `Removed`, `Fixed` read as a verb on the observable behavior.
- Say why it matters when the effect alone does not carry it, in the same sentence.
- Issue or PR references only when the file already carries them, in the file's own format.
- Hyphens only, never em-dashes or en-dashes.

```
Bad   - Refactored the sizing module into smaller functions.
Good  (no entry - nothing on the surface moved)

Bad   - Renamed the sync command handler and updated its tests.
Good  - Renamed the `sync` command to `push`. `sync` is gone, update any scripts that call it.

Bad   - Optimized the backtest engine and the test suite.
Good  - `neh backtest` gets through a year of data in about a third of the time.
Good  (no entry for the test suite - nobody outside the repository runs it)

Bad   - Fixed bug in market.py.
Good  - Fixed positions being sized against stale balances after a partial fill.

Bad   - Added GET /api/v2/markets to MarketController.
Good  - Endpoint for listing tracked markets with their current spreads.

Bad   - Changed the config path.
Good  - Moved configuration to `~/.config/neh/config.toml`. Move the existing file before upgrading, it is no longer read from the old path.
```

### 8. Confirm

Show the exact bullets under the exact headings they will land in. Below them, name in one line what you dropped as internal (`skipped as internal: test-suite speedup, module split`), so a wrong drop is caught before the file is written. Then ask with the `questionnaire` tool for a single `Add to CHANGELOG.md`. Any other reply is a correction: apply it, show it again, ask again.

### 9. Insert

1. Ensure `## [Unreleased]` exists as the first version heading, directly after the preamble. Create it if it is missing, along with its link reference if the file uses them.
2. Inside `[Unreleased]`, find the `### <Category>`. If it is absent, insert the heading in canonical order among the categories already present.
3. Append the bullet as the last item of that category's list.
4. Preserve the file byte for byte outside the insertion: bullet marker, blank lines around headings, indentation of wrapped lines, trailing newline. Never re-wrap or re-flow an existing line.
5. Use one `edit` call, with one entry per insertion point and the smallest unique anchor.
6. Read the changed region back and confirm the file is otherwise untouched.

Never touch a released section, reorder or reword existing entries, add a category heading you have nothing to put under, or clean up unrelated parts of the file.

## Cut a release

Promoting `[Unreleased]` to a version, and nothing else.

1. Stop if `[Unreleased]` holds no entries: there is nothing to release.
2. Establish the version. Take it from the user, or propose one from the entries and confirm it: breaking changes or removals mean a major bump, new features a minor, everything else a patch. Say which entries drove the decision. It is always the *next* version - after 1.4.2 it is 1.4.3, 1.5.0 or 2.0.0 and nothing else - so a number that skips a step is a typo, whoever supplied it.
3. Establish the date with `date --iso-8601`. Never guess it, never take it from a previous session.
4. Rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, keeping its categories and entries in place, and insert a fresh, empty `## [Unreleased]` above it. No category headings under the new one.
5. Update the link references if the file has them: point `[unreleased]` at `<repository>/compare/<tag>...HEAD` and add `[X.Y.Z]: <repository>/compare/<previous tag>...<tag>`. Copy the existing tag spelling (`v1.2.3` or `1.2.3`) and take the repository URL from `git remote get-url origin` or `gh repo view`. For a first release, that link is the tag's own release URL instead of a comparison.
6. For a version pulled because of a serious bug or vulnerability, mark the heading `## [X.Y.Z] - YYYY-MM-DD [YANKED]`. The brackets are loud on purpose.
7. Report what was not done: no tag, no commit, no version bump in any other file. Then report what committing it will do. Where a release workflow reads this file - check the CI configuration for the changelog's path - say plainly that landing this section on the default branch is what publishes the release, and that the version and the notes will be exactly what was just written. Nobody should discover that from the notification.

## Create the file

Write `CHANGELOG.md` at the root of the project or package, exactly this:

```markdown
# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]
```

Drop the Semantic Versioning sentence if the project does not version that way. Do not invent history for versions that shipped before the file existed: mention that past releases are missing, and only backfill them if the user asks, curated by hand rather than from `git log`.

## Format rules

Everything the file itself does not already decide:

- Newest version first, `[Unreleased]` above all of them.
- Every released heading carries its date in ISO 8601, `## [1.4.0] - 2026-08-12`. Inside a changelog this beats the `DD.MM.YYYY` house style, because it sorts, it is unambiguous worldwide, and the specification requires it.
- Versions and sections are linkable: `## [1.4.0]` with a matching reference in the block at the bottom of the file.
- No empty sections. A category heading exists only when it has entries.
- Yanked releases stay in the file, marked `[YANKED]`.
- `[Unreleased]` never gets a date, and released sections are never edited afterwards except to correct something that was wrong.
